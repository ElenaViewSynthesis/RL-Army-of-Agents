# Task: Add a Triton backend + kernel-provenance GRPO reward to CUDA-Agent (2-hour timebox)

## Context (read this; do not re-derive it)

**Paper** — "CUDA Agent: Large-Scale Agentic RL for High-Performance CUDA Kernel Generation" (arXiv 2602.24286). Three components: (1) data synthesis composing ≤5 torch operators into fused tasks, filtered by executability/determinism/non-constant outputs/1–100 ms eager runtime → CUDA-Agent-Ops-6K; (2) a *skill-augmented* environment — a SKILL.md formalising profile → write kernels in `kernels/` → compile → `utils.verification` → `utils.profiling` → iterate, plus anti-hacking: permission-locked `utils/`, a context manager blocking `torch.nn.functional.*` during verification, 5 random-input checks at atol/rtol=1e-2, warmup + averaged timing, no web tools; (3) a milestone reward
`r = -1` if correctness fails, `3` if >5% faster than both eager and torch.compile, `2` if >5% faster than eager only, `1` otherwise — shown to beat a raw-speedup reward. The paper trains with PPO + a critic (value pretraining) and a DAPO-style asymmetric clip (0.2 / 0.28), after single-turn RL warm-up and RFT actor init; its reported collapse mode is importance-ratio variance on low-probability CUDA tokens. Triton is never mentioned.

**We use GRPO-family algorithms, not PPO.** Consequences: no critic → the value-pretraining stage is gone, so stability rests on RFT warm-up, clipping, and group handling; advantages are group-relative over G rollouts of the *same task*; with a discrete reward in {-1,1,2,3}, groups where all G rollouts tie have zero advantage. The paper's critic was also what stopped trajectory-length explosion; without it, the turn cap / overlong term in the reward below is doing that job.

**Repo** — https://github.com/BytedTsinghua-SIA/CUDA-Agent. Only the environment is released, under `agent_workdir/`: `SKILL.md`; `model.py` (`Model`, `get_inputs`, `get_init_inputs`); `model_new.py` (`ModelNew` calling `cuda_extension.*`); fixed `binding.cpp`/`binding_registry.h` (`REGISTER_BINDING`); example `kernels/axpby.cu` + `kernels/axpby_binding.cpp`; `utils/compile.py` (cpp_extension `load` → `cuda_extension.so`), `utils/verification.py` (5 checks, `block_torch_functional()`, hardcoded `.cuda()`), `utils/profiling.py` (torch.profiler CUDA device-time, 5 warmup / 10 iters, prints eager / compile / extension µs). No RL training code, no weights, no agent loop.

**The gap you will exploit.** `block_torch_functional` only patches `torch.nn.functional`. `torch.matmul`, `torch.sum`, `x @ w.T` etc. in `model_new.py` pass verification *and* profile as fast — the ban exists only as instruction text. The reward cannot distinguish "the agent wrote the kernel" from "torch wrote the kernel". None of the paper's five countermeasures closes this.

## Scope boundary — read before planning

**Actually running RL training is out of scope for this session**: the repo ships no training code or weights. GRPO/DAPO show up here as the advantage/reward module the environment feeds, plus mock-rollout tests.

**Phase 2 (separate session)**: real RL rollouts on **2× H200 via Modal** — one GPU serving the policy with vLLM/SGLang, one GPU as the kernel sandbox pool, env tasks dispatched as Modal functions. Everything you build today must be callable from that setup without refactoring: pure-Python, JSON-serialisable reward/advantage code with no torch import; one entry point that takes a task workdir and returns a dict; no global state, no `sudo`, no reliance on cwd beyond the workdir argument.

**Phase 3 (separate session)**: a controlled **GRPO vs DAPO** experiment on the same task set, seeds and budget, reporting which returns the best KernelBench-style metrics (pass rate, faster-rate vs compile, geomean speedup, mean reward, trajectory length, collapse step if any). **MLflow** is the model registry (one registered model per algorithm, one version per checkpoint, params = `RolloutConfig.to_dict()` + trainer hparams, metrics = eval table). **Weights & Biases** is the live observability layer (per-step reward/advantage stats, `frac_dropped`, entropy, IS-ratio clip fraction, turn-count histograms, provenance share, one run per `(algo, seed)`, grouped by `algo`). The two algorithms differ in exactly four places and a fair comparison must toggle each independently: (a) clip range — symmetric 0.2/0.2 vs clip-higher 0.2/0.28; (b) dynamic sampling — keep tied groups vs drop them; (c) loss aggregation — sequence-level vs token-level; (d) overlong shaping — hard cutoff vs soft linear penalty near the cap. (a) and (c) belong to the trainer; **(b) and (d) belong to the environment you build today**, so they must be switches in `RolloutConfig`, not hard-coded behaviour. Do **not** write Modal, trainer, agent-loop, MLflow or W&B code today — but every dict you return must be flat, JSON-serialisable and stably keyed so phase 3 can `wandb.log(result)` and `mlflow.log_params(cfg.to_dict())` without a translation layer.

**Phase-2/3 design decisions to keep in mind (they shape today's interfaces, not today's work).** The thing to decide early is the policy size: on 2×H200 you can do an 8B-class model with vLLM on GPU 0 and a Megatron-Bridge trainer on GPU 1 comfortably, but the paper's agent loop runs 128k context and up to 150 turns — you'll want to cap turns (~20) and context (~32k) for the first runs or a single rollout will eat your sandbox GPU for minutes. Those caps must be **CLI arguments, not constants**: the agent loop enforces turns and context, the environment enforces a wall-clock timeout per task, and both read from one `RolloutConfig` so the numbers can't drift apart. A timed-out task returns reward `-1` with reason `"timeout"`, never hangs the caller.

## The idea

Make the environment **backend-pluggable (CUDA and Triton)** and add a **kernel-provenance gate** to the reward: from the torch.profiler CUDA events the repo already collects, attribute device time to (a) kernels the agent authored, (b) allowed library kernels, (c) torch/aten kernels, (d) memcpy/memset. A rollout earns the milestone reward only if ≥90% of non-memcpy device time is in (a)+(b). Then feed those rewards into a **group-advantage module** with GRPO and DAPO presets. Triton is the natural second backend: Python-only JIT, no `.so`, `tl.dot` for GEMM, and `TRITON_INTERPRET=1` gives CPU-only correctness tests for CI.

## Deliverables (priority order — stop when the timebox ends)

1. `utils/backend.py` — `detect_backend(workdir)` → `"cuda"`|`"triton"` (import of `cuda_extension` → cuda; import from `kernels.triton` → triton; module-level `BACKEND = ...` overrides). `agent_kernel_names(workdir)`: cuda → `__global__` names parsed from `kernels/*.cu`; triton → `@triton.jit` function names from `kernels/triton/*.py`. Add `DEVICE = os.environ.get("CUDA_AGENT_DEVICE", "cuda")` and use it in verification/profiling in place of hardcoded `.cuda()`.
2. `utils/compile.py` — `--backend auto|cuda|triton`. Triton path: import `kernels.triton`, run `ModelNew` once on `get_inputs()` under `no_grad` to force JIT + autotune; print `Compile success` / the Triton error in the same `[TIME]`/exit-code format as the nvcc path. No `.so`.
3. `utils/profiling.py` — keep the existing stdout line byte-identical; add `--json` emitting per-kernel device time and provenance shares `{agent, library, torch, memory}`. Classify by event name: contains an `agent_kernel_names()` entry → agent; `at::native`/`aten` → torch; `cublas|cutlass|cudnn` → library for cuda backend, **torch** for triton backend; `Memcpy|Memset` → memory. Warmup 20 when backend is triton (autotune must finish before timing).
4. `utils/config.py` — **pure Python.** `@dataclass RolloutConfig` with fields and defaults:
   - env: `backend="auto"`, `iters=10`, `timeout_s=180`, `provenance_threshold=0.90`, `speedup_margin=0.05`
   - loop caps: `max_turns=20`, `max_context_tokens=32768`
   - algorithm: `algo="grpo"|"dapo"`, `group_size=8`, `adv_norm="std"|"none"` (std = GRPO, none = Dr.GRPO), `filter_tied_groups: bool`, `overlong_buffer_turns: int` (0 = hard cutoff), `clip_low=0.2`, `clip_high=0.2`, `loss_agg="seq"|"token"`, `kl_coef=0.0`
   - experiment: `seed=0`, `run_name=""`, `tags: list[str]`
   `RolloutConfig.preset("grpo")` → symmetric clip, no tied-group filter, seq-level, hard cutoff, `kl_coef=0.001`. `RolloutConfig.preset("dapo")` → `clip_high=0.28`, `filter_tied_groups=True`, `loss_agg="token"`, `overlong_buffer_turns=4`, `kl_coef=0.0`. `add_args(parser)` exposes every field as `--kebab-case` with the preset applied first so `--algo dapo --clip-high 0.3` overrides just one knob; `from_args`, `to_dict()` (flat, JSON-safe, stable key order — this is what goes to MLflow params and W&B config).
5. `utils/reward.py` — **pure Python, no torch import.** `compute_reward(verify_ok, t_eager, t_compile, t_gen, provenance, cfg, turns_used=None) -> {"reward": float, "reward_base": int, "reason": str, "overlong_penalty": float}`: `reward_base` is eq. (1) exactly with `cfg.speedup_margin`; provenance < threshold → `-1`, reason `"provenance"`; `turns_used > cfg.max_turns` → `-1`, reason `"max_turns"`. Overlong shaping: if `cfg.overlong_buffer_turns > 0` and `turns_used` is within the buffer below `max_turns`, subtract a linear penalty in `(0, 1]` (DAPO-style) so `reward = reward_base - overlong_penalty`; otherwise `overlong_penalty = 0`. `turns_used=None` skips both turn checks. Document that `reward_base` stays in `{-1,1,2,3}` and `reward` is a float only under DAPO shaping.
6. `utils/grpo.py` — **pure Python, no torch import.** `group_advantages(rewards, adv_norm, eps=1e-6)`. `filter_groups(groups, enabled)` drops zero-variance groups only when `enabled`; always returns `(kept, dropped_count)`. `build_batch(task_ids, rollouts, cfg)` groups by task with `cfg.group_size`, applies both per `cfg`, returns flat `(rollout_id, advantage)` pairs plus a flat stats dict with stable keys: `adv/frac_dropped`, `adv/mean`, `adv/std`, `reward/mean`, `reward/frac_3`, `reward/frac_provenance_fail`, `reward/frac_max_turns`, `reward/mean_overlong_penalty`, `turns/mean`, `turns/p95`. Unit-test both presets on identical synthetic groups and assert: DAPO drops the all-tied group and GRPO keeps it with zero advantages; mixed groups sum to ~0 under both; a `-1` provenance rollout has the most negative advantage; overlong penalty is 0 under GRPO preset and >0 under DAPO for `turns_used = max_turns - 1`.
7. `utils/rollout_env.py` — the phase-2 entry point. `run_task(workdir: str, cfg: RolloutConfig, turns_used: int | None = None) -> dict` running compile → verification → profiling → `compute_reward` inside `workdir` via subprocess with `cfg.timeout_s` (not import, so a crashing or hanging kernel can't take the caller down). Returns a **flat** dict: `env/verify_ok`, `env/t_eager_us`, `env/t_compile_us`, `env/t_gen_us`, `env/speedup_vs_compile`, `env/provenance`, `env/wall_s`, `env/turns_used`, `reward/value`, `reward/base`, `reward/reason`, `reward/overlong_penalty`, `meta/backend`, `meta/task_id` (basename of workdir), `meta/algo`, `meta/seed`, plus `log/compile_tail` and `log/stderr_tail` (strings; phase 3 strips `log/*` before `wandb.log`). Timeout → reward `-1`, reason `"timeout"`, subprocess killed. Safe to call concurrently on different workdirs; honours `CUDA_VISIBLE_DEVICES`. CLI: `python -m utils.rollout_env <workdir> [RolloutConfig args] [--turns-used N]` printing the JSON. `--turns-used` exists only so the CLI can exercise the turn paths without an agent loop.
8. `kernels/triton/__init__.py` + `kernels/triton/axpby.py` — `@triton.jit` `axpby_kernel` with `triton.autotune` over 2–3 block sizes and `axpby_forward(a, b, alpha)` allocating only via `torch.empty_like`.
